## Why

Twice in the Hostman demo logs of 08/09, minutes apart, with nothing wrong on either side:

```
sqlalchemy.exc.OperationalError: (psycopg2.OperationalError)
SSL connection has been closed unexpectedly
  -> GET /api/agents                        500
  -> GET /api/emailing/microsoft/status     500
```

The async engine has carried `pool_pre_ping` and `pool_recycle` since it was written (`helpers/database.py`). The synchronous stores never did: they are module-level singletons whose pooled connections outlive anything a managed cluster keeps open. The cluster closes one, the pool hands it out anyway, psycopg2 raises, the router answers 500.

## What

`helpers/sync_engine.py` — `create_sync_engine(url, **kwargs)`: `pool_pre_ping=True` (one round-trip per checkout, turning a dead connection into a transparent reconnect) and `pool_recycle=300` (retire it before the cluster's idle timeout), both overridable. Applied to the five engines that live as long as the process: `agent_manager`, `hub_manager`, `api_key_store`, `skill_manager`, `tool_config`.

The one-shot migration engines are deliberately left alone: they run once at boot and hand their connection straight back.

## Tests

`tests/test_sync_engine_resilience.py` (8): the helper's defaults; an explicit option still wins; a real engine reports `pool._pre_ping`; and — the one that matters for the next store — each of the five modules is **read as source** to assert it builds its engine through the helper and no longer calls `create_engine` directly.

CI-equivalent suite: 136 reds, exactly the same set as `origin/main` — difference empty.
